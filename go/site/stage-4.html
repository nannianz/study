目标：理解 goroutine 与 channel，建立「并发要考虑数据竞争」的意识——JS 单线程思维的最大转变。未开始

JS 对照重点

JS 对照

单线程事件循环 vs 多协程真并行：JS 的 async 是「协作式调度」，goroutine 是抢占式、可跑满多核。

go func(){...}() ≈ 触发异步任务，但通信方式完全不同：JS 靠 Promise 链/回调取值，Go 靠 channel 传值（值发过去，不是共享变量）。

channel ≈ MessageChannel/消息队列，但有阻塞语义：没人收就卡住（这正是 Go 想要的同步点）。

数据竞争要加锁（Mutex）——JS 永远不需要锁，这章是思维转变最大的一章。

第一课 · goroutine 与 channel 讲义就绪 · 未开课

覆盖 ch26 上半。练习落在 code/09-goroutine/。

1. goroutine：go 一个函数就是并发（完整版）

func worker(id int) {
    fmt.Printf("协程 %d 开工\n", id)
}

func main() {
    for i := 1; i <= 5; i++ {
        go worker(i)          // 加个 go 前缀 → 这个函数跑在新协程里，立即返回继续循环
    }
    fmt.Println("main 已经跑完了，不等它们")
    // ← 大概率一个协程都没打印：main 协程退出，其他协程直接陪葬
}
go func() {                  // 匿名函数版本（back 里最常见的形态）
    fmt.Println("并发干活")
}()                           // 注意：go 定义完要立刻 () 调起来

协程是 Go 运行时调度的轻量线程（初始栈 2KB，对比系统线程 1MB），百万个不费劲。两个铁律：main 退出全家陪葬（所以需要「等」的机制——下节课 WaitGroup）；调度顺序不可预测（把上面 `main 已经跑完了` 换成 `time.Sleep(time.Second)` 多跑几次，1~5 的打印顺序每次不同——goroutine 不是排队执行）。

2. channel：协程间的传值管道（完整版）

// 生产者消费者：最经典的完整模型
func produce(ch chan<- string) {       // chan<- 只发送（方向限定，阶段 3 学的类型语法）
    for i := 1; i <= 3; i++ {
        ch <- fmt.Sprintf("任务%d", i)  // 发送：没接收者就阻塞等
    }
    close(ch)                          // 生产完关闭——告诉消费者「没有更多了」
}

func main() {
    ch := make(chan string)            // 无缓冲：发送和接收必须同时就位（交接棒）
    go produce(ch)

    for task := range ch {             // range 持续接收；channel 关闭且读空后自动退出循环
        fmt.Println("收到:", task)      // 任务1 / 任务2 / 任务3（顺序稳定——单个 channel 保证次序）
    }
    fmt.Println("生产者已关闭，消费者退出")
}
ch2 := make(chan int, 3)   // 带缓冲：先备 3 个格子
ch2 <- 1; ch2 <- 2; ch2 <- 3   // 装满前发送不阻塞
// ch2 <- 4                  // ← 第 4 个阻塞，直到有人取走一个

// 关闭后的接收语义（三段论）：
v, ok := <-ch2            // comma-ok 第三兄弟！map 判存在/类型断言/channel 判开没关
                           // 关闭后：先收到历史值 (v, true)，收完收到零值 (0, false)
// ch2 <- 9                // ← 向已关闭 channel 发送 = panic（关闭由发送方做，接收方永远别 close）

口诀：不要通过共享内存来通信，而要通过通信来共享内存——数据从一个协程「发」给另一个（值拷贝过去），而不是两个协程抢同一个变量。nil 容忍表补最后一行（阶段 2 那张表的缺项）：nil channel 收发都永久阻塞——不 panic、死等，select 里常用来「关掉」某个分支。

3. JS 对照

JS 对照

调度模型：JS 单线程事件循环，async 是「协作式」排队（一个死循环全卡）；goroutine 多核真并行、抢占式——失去「反正单线程不会打架」的安全感。

取值方式：JS 异步拿结果靠 Promise.then/await（注册回调，不阻塞）；v := <-ch 是真的阻塞等待——协程挂起让出 CPU，值到了再醒。channel ≈ MessageChannel + 阻塞语义；「交接棒」式同步 ≈ 无缓冲 channel。

闭包捕获坑（JS 老朋友）：for i := ... { go func(){ fmt.Println(i) }() } 在 Go 1.22 前所有协程共享循环变量 i（打印全是最后一个值）——和 JS 的 var 循环捕获坑一模一样，Go 1.22 起才修成每次迭代新变量（≈ JS 的 let）。back 里的防御写法是老风格但永远正确：go func(id int){...}(i) 参数传值。

易踩坑 ×2：① main 不等就退出，协程白跑；② 无缓冲 channel 同一协程自发自收 = 死锁（fatal error: all goroutines are asleep）。

第二课 · sync 包与 select 讲义就绪 · 未开课

ch26 下半（教程较浅，对照 back 补齐）。练习落在 code/10-channel/。

1. WaitGroup：等一群协程干完（完整版）

func main() {
    var wg sync.WaitGroup
    for i := 1; i <= 5; i++ {
        wg.Add(1)                    // 计数 +1（在起协程之前 Add）
        go func(id int) {            // 把 i 当参数传值进闭包——阶段 2 值拷贝知识复用
            defer wg.Done()          // 干完 -1（defer 保证 panic 也减，计数不泄漏）
            time.Sleep(time.Duration(id*100) * time.Millisecond)
            fmt.Printf("协程 %d 完成\n", id)
        }(i)
    }
    wg.Wait()                        // 阻塞到计数归零
    fmt.Println("全部干完，main 安全退出")
}

三件套口诀：Add 在前、Done 在 defer、Wait 收尾。Add 放进协程体内是竞态（main 可能先 Wait 了计数还是 0）。

2. Mutex：给共享变量上锁（完整版）

func main() {
    var (
        counter int
        mu      sync.Mutex
    )
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()                // ← 注释掉这两行跑 -race，看结果小于 1000
            counter++                // 读-改-写三步，不是原子的！
            mu.Unlock()
        }()
    }
    wg.Wait()
    fmt.Println(counter)             // 加锁：恒 1000；不加锁：大概率 <1000（静默丢更新）
}

验证手段：go run -race main.go——竞态检测器，报 WARNING: DATA RACE 就是锁没加对。注意go run 默认不查竞态，必须显式 -race（JS 世界没有对应物——单线程根本不需要）。

3. select：多路复用（完整版）

func main() {
    ch := make(chan string)
    go func() {
        time.Sleep(2 * time.Second)   // 故意慢
        ch <- "结果来了"
    }()

    select {
    case v := <-ch:                   // 谁先就绪走谁
        fmt.Println("收到:", v)
    case <-time.After(1 * time.Second):   // 1 秒兜底计时器
        fmt.Println("超时放弃")          // ← 这条先到：打印这个，main 退出
    }
}

select 每次随机挑一个已就绪的分支执行；都没就绪就阻塞（有 default 则立即走 default）。time.After 每次调用造一个新计时器 channel——超时控制的标配。把 sleep 改成 500ms 再跑，「收到」分支就赢了。

4. JS 对照

JS 对照

数据竞争是 JS 不存在的概念——单线程下 counter++ 永远安全（Worker 也不共享普通变量）。Go 多核并行下两个协程同时 counter++ 会互相覆盖丢更新——不是崩溃，是静默算错，比崩溃可怕（计数少了、统计歪了，没人报错）。原则：变量被多个协程读写 → 要么锁、要么收拢到单协程经 channel 访问。

select ≈ Promise.race（谁先到处理谁，time.After 分支 = 超时兜底）；WaitGroup ≈ Promise.all。微妙差异：Promise.race 输了的那条 Promise 还在跑（只是结果被忽略）；select 没选中的分支没副作用——配合 context 取消才能真正掐掉慢任务（阶段 7 见 smb 实战）。

5. back 对照 + 练习

back 真实代码 ×2

smb 并发统计——service/liststats/concurrent.go:29，聚合多个统计源、并发拉取、超时兜底（本课三件套全用上）：

ctx, cancel = context.WithTimeout(ctx, timeout)   // 超时控制（context 是 select 的实战搭子）
defer cancel()
var wg sync.WaitGroup
for _, fn := range fns {
    wg.Add(1)
    go func(f func(context.Context)) {
        defer wg.Done()
        f(ctx)                                       // 每个统计源并发跑
    }(fn)
}
wg.Wait()                                            // 全部回来（或超时）再聚合

net_scan 的 SSH 客户端（ssh_client/ssh.go:401）用 select 做命令执行超时；remotessh、scheduler 的可取消任务靠 channel + select + context 组合——「select 管『谁先到』，context 管『喊停』」。
