第一课 · net/http 裸写 讲义就绪 · 未开课

实战热身：不用框架写一个 HTTP 服务，知道 gin 帮你省了什么。练习并入 code/13-gin/。

func main() {
    http.HandleFunc("/api/devices", func(w http.ResponseWriter, r *http.Request) {
        switch r.Method {
        case http.MethodGet:
            w.Header().Set("Content-Type", "application/json")
            json.NewEncoder(w).Encode([]string{"d1", "d2"})
        case http.MethodPost:
            var d Device
            json.NewDecoder(r.Body).Decode(&d)
            w.WriteHeader(http.StatusCreated)
        }
    })
    http.ListenAndServe(":8080", nil)
}
JS 对照

≈ node 原生 http.createServer + 手动路由——没框架时 Node 也这么苦。痛点同步显现：路由参数要手切 URL、中间件要手串、没有统一 JSON 响应。这些痛点就是 gin 存在的意义，下节课逐一对照。

back 对照

标准库的 Handler 接口 ServeHTTP(w, r) 是一切 Go Web 框架的地基——gin 的 engine 实现的就是它。

第二课 · gin 框架 讲义就绪 · 未开课

练习落在 code/13-gin/。net_scan/smb 的骨架。

1. 路由与参数

r := gin.Default()                          // 自带 Logger + Recovery 中间件

api := r.Group("/api/v1")                   // 路由组 ≈ Router 挂载
{
    api.GET("/sites/:site_id", getSite)     // 路径参数
    api.POST("/sites", createSite)
    api.PATCH("/sites/:site_id", updateSite)
}

func getSite(g *gin.Context) {              // handler：*gin.Context 是一切
    id := g.Param("site_id")                // 路径参数
    page := g.Query("page")                 // 查询参数 ?page=2
    req := &UpdateRequest{}
    g.BindJSON(req)                          // body → struct（binding tag 校验）
    g.JSON(200, gin.H{"id": id, "page": page})   // 响应 ≈ res.json()
}

2. 中间件

r.Use(func(c *gin.Context) {
    start := time.Now()
    c.Next()                                 // 放行给后续 handler
    log.Println(time.Since(start))           // 回来记耗时
})

3. JS 对照

JS 对照（Express 老家）

RouterGroup ≈ express.Router()；g.Param("id") ≈ req.params.id；g.Query ≈ req.query；BindJSON ≈ body-parser + 校验（校验规则写在 struct tag：binding:"required"）；c.Next() 中间件链 ≈ next()（gin 是先序+后序两段，不是真洋葱）；gin.H ≈ 直接 res.json({...})。

易踩坑：handler 忘 return 是经典 bug——c.JSON 只是写响应不中断函数，后面再写一个 c.JSON 就 double write（back 源码每个错误分支都紧跟 return 的原因）。

4. back 真实代码

back 真实代码

net_scan 的函数式 handler（结构最简）：

func GetDevices(c *gin.Context) {
    repo := storage.NewRepository()
    filter := storage.DeviceFilter{Q: c.Query("q")}
    result, err := repo.ListDevices(c.Request.Context(), filter, ...)
    if err != nil {
        c.JSON(http.StatusInternalServerError, gin.H{"error": err.Error()})
        return
    }
    c.JSON(http.StatusOK, result)
}

smb 的路由注册（组 → controller 循环）：groups["/api/v1"] 传给每个 controller 的 RegisterRoutes——接口 + 隐式实现 + map 在真实框架里的合体。

第三课 · gorm ORM 讲义就绪 · 未开课

练习落在 code/14-gorm/（sqlite 免装数据库）。

1. 连接 + 建表 + CRUD 四式

db, err := gorm.Open(sqlite.Open("dev.db"), &gorm.Config{})
db.AutoMigrate(&Device{})            // 按 struct + gorm tag 建表

db.Create(&Device{Name: "AP1", Price: 99})           // INSERT
db.First(&d, "name = ?", "AP1")                     // SELECT 单条（? 占位防注入）
db.Model(&d).Update("price", 79)                    // UPDATE
db.Where("price > ?", 50).Find(&list)               // SELECT 列表
db.Delete(&d)                                       // DELETE

2. JS 对照

JS 对照

gorm ≈ Sequelize/TypeORM：模型定义（struct+tag ≈ Model+装饰器）、关联、迁移。坑也同款：复杂查询生成的 SQL 不直观，要开日志看真身（db.Debug() ≈ Sequelize logging）。? 占位符 ≈ 参数化查询，字符串拼接 SQL 在两边都是安全红线。

第四课 · 分层架构与终极练习 讲义就绪 · 未开课

练习落在 code/15-gin-crud/——阶段 6 毕业作品。

1. back 的分层地图

cmd/boot.go        入口：组装依赖、启动
api/restserver.go  路由注册：gin 分组 → 各 controller
controller/        参数解析、校验、调 service、统一响应
service/           业务逻辑、事务、DTO 定义
repo/              数据访问（smb: 泛型仓储 / net_scan: storage 包）
model/entity/      struct + 双 tag（阶段 2 精读过的 Site）

一次请求的一生：HTTP → 路由匹配 → controller 解参数 → service 干业务 → repo 读写库 → 原路返回 JSON。每层单向依赖，entity 被所有人引用。

JS 对照

≈ 前端分层心智：routes → pages → api/services → store——只是方向从「渲染」换成「数据处理」。
